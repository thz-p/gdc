资源回收两头堵RUUA问题 - 知识提炼 + 审校

约 7 分钟 · 本页访问
Unity RUUA 内存 AssetBundle Mono 性能优化

一、核心认知

RUUA 调了卡、不调内存涨，问题不在"什么时候调"，而在"调了有没有用"。 先确认 Asset 曲线是否下降，再检查 AB 卸载策略，最后才调整调用时机。
Mono 400MB 不一定多，其它 1GB 才是大头。 先定 PSS 总预算，再判断各模块占比是否合理，优先查"其它"。

二、案例一：RUUA 调了会卡，不调内存又涨

现象

无缝地图项目，RUUA 挂在背包/地图等全屏 UI 上。调了卡，不调内存涨，没有切场景的天然时机。

关键判断

排查顺序要反过来：

  1. 先确认 RUUA 是否真的释放了资源 — 看 UWA GOT Online Asset 曲线，RUUA 调用点前后是否有明显下降
  2. Asset 曲线没变化 → 检查 AssetBundle 卸载策略 — AB 没卸载，RUUA 扫描不到可回收对象，等于"空跑"
  3. 最后才调整 RUUA 调用时机

解决路径

  • 建立 AssetBundle 分级缓存机制：LRU、玩家位置/距离管理 Bundle 生命周期
  • 高优先资源常驻，低优先 Bundle 在 Application.lowMemory 时统一卸载再回收
  • 调用时机：固定间隔轮询（5~10分钟）或监听 lowMemory 回调
  • 挂在全屏 UI 上可行，但必须确保调用有实际收益，不空跑

三、案例二：Mono 与其它同时偏高

现象

Mono 峰值 400MB，Reserved Total 中"其它"接近 1GB，Memory Profiler 定位不到来源。

关键判断

先定 PSS 总预算，再判断 Mono 是否合理：

设备 RAM 建议 PSS 上限
3GB 1.3~1.5GB
4GB 1.8~2.2GB
8GB 持续接近 3GB 仍有被回收风险

Mono 400MB 脱离总预算没有意义。 Mono、纹理、Mesh、Native 等在同一份预算里分配空间，Mono 多占 100MB 意味着其他模块少 100MB。

排查路径

1GB 的"其它"比 Mono 400MB 更值得优先查：

  1. Memory Profiler 分析快照，能定位则优先解决
  2. 无法定位 → UWA Gears / Android Studio 排查 Native Heap
  3. 怀疑 Lua 等脚本引擎 → Perfetto 符号化分析定位分配来源
  4. 交叉验证多种工具，不单凭一个工具下结论

四、可复用排查思路

问题 常见误区 正确切入点
RUUA 调了卡不调涨 不停调整调用时机 先看 Asset 曲线确认是否空跑，再查 AB 卸载策略
Mono 偏高 + 其它 1GB 直接优化 Mono/GC 先定 PSS 总预算，优先查"其它"来源

附：方案审校

案例一审校

✅ 正确。 "RUUA 空跑"的判断非常准确——AssetBundle 不卸载，RUUA 无法回收其资源，这是 Unity 资源管理的基本机制。排查顺序"先确认回收效果→再检查 AB 卸载策略→最后调整调用时机"是正确的方法论。

⚠️ 补充风险点： - LRU 缓存机制需要逐出策略的触发时机明确——是按内存阈值触发（如 PSS 接近预算上限）还是按时间触发，需根据项目实际选型 - Application.lowMemory 回调在 Android 上触发时机因厂商而异，部分设备可能延迟触发甚至不触发，不能完全依赖 - 文章提到"固定间隔 5~10 分钟调用 RUUA"，但未说明间隔期间内存不断增长的风险，若项目有内存泄漏，固定间隔可能无法阻止 OOM

🔧 可行性： 高。Asset 曲线 + AB 卸载策略检查是标准方法。

案例二审校

✅ 正确。 PSS 总预算优先、各模块在同一预算内分配空间、优先查"其它"而非 Mono——这些判断准确且务实。"其它"使用 Memory Profiler → UWA Gears / Android Studio → Perfetto 的递进排查路径合理。

⚠️ 补充风险点： - PSS 值在不同 Android 版本和厂商上的统计口径有差异，建议以 UWA GOT Online 的实测值为准，而非硬性参考"3GB 设备 1.3~1.5GB"的区间 - 使用 Perfetto 排查 Native 分配需要符号化（Symbolication），如果项目未保留符号文件，定位会很困难，需在构建流程中保留 - "其它"内存中可能包含引擎内部缓存（如 RenderTexture 池、Shader 缓存），这些是 Unity 自行管理的，强行分析可能徒劳，需先区分"引擎内部缓存"和"异常泄漏"

🔧 可行性： 高。递进排查路径是业界标准做法。

综合结论

维度 评价
技术深度 良好，准确指出 RUUA 空跑和 PSS 总预算优先两个关键认知
正确性 核心判断无误，无原理性错误
可落地性 高，排查路径具体可操作
风险披露 良好，解释了"其它"难以定位的客观困难
数据可信度 PSS 预算区间为参考值，非普适标准

没有发现原理性错误。 主要提醒：LRU 逐出策略需明确触发时机；lowMemory 回调因厂商而异；PSS 口径因版本/厂商有差异；Perfetto 分析需符号文件。
