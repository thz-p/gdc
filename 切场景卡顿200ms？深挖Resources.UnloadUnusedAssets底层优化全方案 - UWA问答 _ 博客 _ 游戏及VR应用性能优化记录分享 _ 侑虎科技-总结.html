Resources.UnloadUnusedAssets 底层优化方案 — 知识提炼 + 审校

约 12 分钟
Unity 性能优化 IL2CPP GC 多线程 Resources.UnloadUnusedAssets

一、核心痛点

每次切场景，Resources.UnloadUnusedAssets 在主线程同步阻塞 200~300ms（低端机甚至到秒级）。标注的"异步"仅是延迟一帧，主线程并未逃脱阻塞。

Resources.UnloadUnusedAssets();  // 看似异步，实则阻塞主线程 200ms+

下调执行时机

方案不解决"为什么慢"，但解决"什么时候慢"。把不可控的延迟变成可控的延迟。

Resources.UnloadUnusedAssets();
WaitForAllOperationsToComplete();  // 等 GC 跑完再跳战斗
SendMarkLoadingComplete();

二、执行流程拆解（5 阶段）

阶段 耗时占比 说明
① FindAllLiveObjects 低 枚举所有 Native 对象
② MarkSceneRoots 低 标记场景根/Manager 根为存活
③ CreateObjectToIndexMapping 低 建 InstanceID → 索引哈希表
④a MarkStaticDependencies ~49% 遍历 C# 静态字段，递归扫描托管堆。最大热点
④b MarkNormalDependencies ~39% 在 Native 对象图上做 BFS
⑤ CleanupUnusedObjects 低 释放未标记的 Native 资源

④a + ④b 合计占 ~88% 总耗时，是整个优化的主攻方向。

三、优化方案一：标记跳过（SkipLiveness）

思路：让 GC 扫描器看到"不必扫的字段/类"就跳过，减少 ④a 的遍历范围。

借位零开销

在 IL2CPP 元数据的空闲位做标记，运行时一条位与指令判断，O(1)，零内存开销：

  • 字段级：field.attrs 位 3 → FIELD_ATTRIBUTE_SKIP_LIVENESS 0x0008
  • 类级：klass.flags 位 22 → TYPE_ATTRIBUTE_SKIP_LIVENESS 0x00400000
if (field->type->attrs & FIELD_ATTRIBUTE_SKIP_LIVENESS)
    continue;  // 跳过这个字段的 Liveness 扫描

三类标记的生效情况

标记位置 是否生效 原因
类级 [SkipLiveness] ✅ 生效 整个类的实例跳过 Liveness 递归
静态字段 [SkipLiveness] ✅ 生效 单个静态字段跳过
实例字段 [SkipLiveness] ❌ 失效 实例对象走 gc_desc 位图快速路径，不查字段元数据

陷阱：gc_desc 是禁区

gc_desc 不只 Liveness 在用，Boehm GC 分配内存时也用它做精确扫描。如果在 gc_desc 里排除字段，Boehm GC 也会跳过，导致字段引用的对象被错误回收，引发野指针崩溃。

适用范围

安全（可标记） 危险（不可标记）
游戏配置表（纯数据） 持有 Resources.Load 加载的资源
帧同步层对象（无引擎引用） 持有 AssetBundle 加载的 Native 引用
服务器协议对象 持有动态生成未挂场景的 Material/Texture/Mesh
其他纯数据结构 任何拿不准的对象

四、优化方案二：多线程生产者-消费者模型

问题

Worker 处理完初始根（场景根+Manager 根）后闲置，等待主线程跑完 FromStatics。

改造

引入读写索引分离的共享队列，主线程（生产者）实时投放新 Root，Worker（消费者）持续消费，闲置窗口压到接近零。

// 生产者（主线程）
buf[writeIndex] = index;
atomic_store(&writeIndex, writeIndex + 1, release);

// 消费者（Worker）— 多消费者用 CAS 抢 slot
for (;;) {
    int r = readIndex;
    int w = atomic_load(&writeIndex, acquire);
    if (r >= w) {
        if (atomic_load(&scanComplete, acquire) && readIndex >= writeIndex)
            break;
        YieldProcessor(); continue;
    }
    if (!CAS(&readIndex, r, r + 1)) continue;
    MarkDependencies(buf[r]);
}

设计要点

  • 写顺序：数据先落，索引后发布（Release/Acquire 语义）
  • CAS 抢 readIndex：多消费者只有一个能成功，无锁
  • 不用 Ring Buffer：容量按上界 Reserve，索引单调推进到底
  • 复用 JobSystem Worker 线程：不额外开线程池，避免移动端 1MB 栈内存浪费

五、实测效果

机型 优化前 优化后 降幅
骁龙 865 (1+8pro) ~200ms ~50ms 75%

六、更高层面思考

6.1 自动标记

IL2CPP 代码生成器在编译期做静态可达性分析，自动给"闭包不可达 UnityEngine.Object"的 sealed 类打上标记。

bool CanReachUnityObject(TypeDef t, HashSet<TypeDef> visited) {
    if (!visited.Add(t)) return false;
    if (t.IsSubclassOf("UnityEngine.Object")) return true;
    foreach (var f in t.InstanceFields) {
        var ft = f.FieldType.Resolve();
        if (ft == null || ft.IsInterface || !ft.IsSealed) return true;
        if (CanReachUnityObject(ft, visited)) return true;
    }
    return false;
}

6.2 三层架构

层级 职责 解决什么问题
资源框架（Addressables/YooAsset） 显式 Refcount 管理资源生命周期 结构性：解决"该谁释放"的所有权问题
本文的两个优化 扫描尽可能快 局部性：在不能改 API 的前提下做到上限
HideFlags 关键资源不丢 兜底：将判错后果从崩溃降级为内存多占

6.3 UE 对照

UE 有类似的 GC 卡顿问题（Fortnite 的 GC Mark 从 ~66ms 压到 ~22ms）。但 UE 的 UObject 是 GC-aware 设计，修补成本更低。Unity 的痛点根因在于双对象世界（C++ Native + C# Managed 两张图），IL2CPP 是额外的一道墙。

200ms 不是 Unity 独有的，而是"全图可达性扫描"这个通病在双对象世界里的重症形态。

附：优化方案审校

SkipLiveness 标记跳过

✅ 技术原理正确。 IL2CPP 元数据存在空闲位、静态字段与实例字段走不同扫描路径、gc_desc 是 Boehm GC 共享禁区——这些关键判断均准确无误。

⚠️ 主要风险： - IL2CPP 版本升级：借用的空闲位可能在 Unity 升级时被官方占用，不会收到通知，需每次跨版本做二进制比对 - 人工审计负担：中大型项目的类型闭包极复杂，人工可达性分析容易漏审。漏标后果是运行时崩溃，排查成本极高 - has_references 截断风险：has_references && !skip 会将整个类的 Native 引用链全部截断——如果类中混入一个持 Resources.Load 引用的字段，该资源会被误回收

🔧 可行性： 技术上可行，但需团队具备 IL2CPP 运行时 + 代码生成器的修改能力，建议搭配自动静态分析一起做。

多线程生产者-消费者模型

✅ 设计合理。 读写索引分离、Release/Acquire 内存序、CAS 抢 readIndex、复用 JobSystem Worker 线程——这些设计决策均正确且务实。

⚠️ 需要注意的细节： - scanComplete 同步：主线程必须写完所有数据后才设置 scanComplete = true，且用 release 语义保证 Worker 的 acquire 能看到所有前置写入 - 忙等对移动端的影响：YieldProcessor spin-wait 在低端机上可能影响功耗和发热 - Worker 线程可用性：大部分情况下 JobSystem 在 GC 期间无其他任务，但并非绝对保证

🔧 可行性： 高度可行，本质上是 Unity 2022 官方多线程 GC 实现思路的复现。

综合结论

维度 评价
技术深度 优秀，对 IL2CPP 运行时和 GC 流程理解准确
正确性 核心逻辑正确，无原理性错误
可落地性 SkipLiveness 需团队有 IL2CPP 修改能力；多线程优化相对普适
风险披露 诚实，作者明确说明了适用范围和危险边界
数据可信度 75% 降幅是单设备单场景参考值，非普适承诺

没有发现原理性错误。 主要风险在于 SkipLiveness 的人工审计成本和 IL2CPP 版本兼容性。
