Unity UGUI DrawCall Camera 渲染优化

一、核心认知

视觉复杂度 ≠ 渲染开销。 UI 画面看起来不拥挤，但只要产生大量独立绘制批次，渲染提交开销照样高；Camera 只渲染一个物体，也仍需完整走一遍渲染准备、可见性判断、队列处理、指令提交流程。

本篇来自 UWA 第 486 期技术分享，两个案例都是"画面简单但开销高"的典型反直觉问题。

二、案例一：UI 简单，DrawCall 为何接近 400

现象

指标 数值 说明
Canvas.RenderSubBatch 峰值 394 次 该节点调用次数 ≈ UGUI DrawCall 数
UGUI DrawCall 300~400 UI 侧提交批次处于高水平
UI 模块 CPU 均耗时 7.85ms 60FPS 帧预算 16.67ms，UI 占近一半

根因

  • 玩法表现通过 UI 组件实现，叠加 UI 特效、TMP 文本，实际参与渲染/更新的 UI 对象很多
  • 动态 UI 与大量静态 UI 混在同一 Canvas，少量元素变化扩大更新影响范围
  • 主要耗时入口是 UpdateBatches（处理 UI 元素更新和渲染批次整理）

定位路径

  1. 看 Canvas.RenderSubBatch 调用次数 → 观察 UGUI DrawCall 变化
  2. 看渲染模块与 UGUI 耗时曲线相关性 → 强相关说明波动来自 UI 侧
  3. 在 Canvas.SendWillRenderCanvases 插桩，运行时记录触发更新的 UI 对象（参考雨松MOMO 网格重建定位法）

优化方向

  • 检查各类 UI 元素合批情况，消除不必要的批次拆分
  • 高频变化 UI 与静态 UI 拆分到不同 Canvas，缩小每次更新影响范围

三、案例二：单模型额外 Camera 耗时接近 UI Camera

现象

为避免近裁剪面裁切模型，加了一个只渲染该模型的额外 Camera，平均耗时却接近常驻 UI Camera。

根因

Camera 的成本不只取决于它绘制了多少物体。

即使画面只有少量内容，新增 Camera 仍需独立完成：渲染准备 → 可见性判断 → 渲染队列处理 → 指令提交。显示内容数量 ≠ Camera 渲染成本。

定位路径

  1. 看 Stacks 节点确认 Camera 数量变化（常规 2 个 → 玩法 3 个 → 过场 4 个）
  2. 查 Camera 耗时堆栈，确认 Culling 等管线节点占比
  3. 三态对比测试：保留原配置 / 调整 Culling Mask / 完全关闭，区分模型渲染成本与 Camera 流程开销
  4. 逐项核对：阴影、后处理、Occlusion Culling、独立 RenderTexture 是否必要
  5. 确认过场时主场景 Camera 与额外 Camera 是否重复渲染

优化方向

  • 控制 Camera 启用时机，仅在需要时开启
  • 关闭与当前显示需求无关的功能
  • 配置精简后仍高 → 评估纳入已有 Camera 流程或用 Renderer Feature 替代额外 Camera

判断标准

当一个仅用于显示单个模型的 Camera，其平均耗时已经接近常驻 UI Camera 时，就应将其列为重点排查对象。

四、可复用的排查思路

问题特征 第一切入点 关键指标/工具
画面简单但 UI 开销高 DrawCall 数 & UpdateBatches Canvas.RenderSubBatch、SendWillRenderCanvases 插桩
画面简单但渲染耗时高 Camera 数量 & 堆栈 Stacks 节点、Culling 耗时、三态对比

附：方案审校

案例一审校

✅ 正确。 "视觉复杂度 ≠ 渲染开销"是 UGUI 性能分析的核心前提。RenderSubBatch 调用次数近似 DrawCall 数、UpdateBatches 是主要耗时入口、动态/静态 UI 混合扩大重建范围，这些判断均符合 UGUI 实现机制。

⚠️ 补充风险点： - DrawCall 高不一定是性能瓶颈，需结合 SetPass Call（材质切换次数）一起看，SetPass Call 才是真正的 GPU 状态切换成本 - TMP 文本除破坏合批外，字体图集（Atlas）溢出会触发重建且易被忽略，排查时应检查 Atlas 使用率 - 拆分 Canvas 能缩小重建范围，但会增加 DrawCall（Canvas 之间不合批），需在"重建成本"与"合批收益"间权衡，不是越细越好

🔧 可行性： 高。SendWillRenderCanvases 插桩定位法成熟可靠，雨松MOMO 的方案可直接复用。

案例二审校

✅ 正确。 "Camera 成本不取决于绘制物体数量"判断准确。Camera 的固定管线开销（Culling、阴影投射、后处理等）确实与可见物体数量弱相关。

⚠️ 补充风险点： - 额外 Camera 若开启阴影，会参与全局 ShadowMap 渲染，成本可能远超模型本身 - 额外 Camera 渲染到独立 RenderTexture 时，RT 的分辨率和格式对带宽/显存影响大，需核对 - "纳入已有 Camera 流程"需注意渲染顺序和 Clear 标志，否则可能引入深度冲突或画面错乱 - URP 下用 Renderer Feature 替代额外 Camera 是更优解，但需确认 Feature 的渲染时机（BeforeRendering/Opaque 等）符合需求

🔧 可行性： 高。三态对比测试是排查 Camera 开销的标准方法论，结论可信。

综合结论

维度 评价
技术深度 良好，准确点出 UGUI 与 Camera 开销的反直觉特性
正确性 核心判断无误，无原理性错误
可落地性 高，定位路径具体可操作
风险披露 诚实，明确说明"耗时接近 ≠ 配置异常"，避免误判
数据可信度 394 次、7.85ms 为单项目实测参考值，非普适阈值

没有发现原理性错误。 主要提醒：DrawCall 数应结合 SetPass Call 看；拆分 Canvas 需权衡重建与合批；额外 Camera 的阴影/RT 成本易被低估。
