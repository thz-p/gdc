高频GC与特效精准降温 - 知识提炼 + 审校

约 8 分钟 · 本页访问
Unity GC 增量GC 特效 Overdraw 1/4 RT GPU 性能优化

一、核心认知

GC 频繁不是 GC 本身的问题，而是业务代码持续制造垃圾对象。 排查重点不在"GC 调了多少次"，而在"哪些代码在持续制造垃圾"。
特效降温要精准，别急着对整体画质动刀。 1/4 RT 解决特效自身 GPU 压力，降场景分辨率影响整个画面，优化范围不同，应按瓶颈来源分层施策。

本篇来自 UWA 第 484 期技术分享，两个案例分别治"高频 GC"和"特效 GPU 压力"。

二、案例一：没有主动调用，为什么 GC 依然频发

现象

部分设备运行一段时间后 GC 次数异常高，但项目没有主动调用 GC，也没有明显大量内存申请。

根因

GC 不需要显式 GC.Collect 才会发生，持续产生大量临时对象就会被迫触发 GC。

  • 高频代码持续产生临时对象，例如 Tick 中字符串拼接：string msg = "hp:" + hp + " mp:" + mp;
  • 单次分配不明显，但在高频路径中不断产生新字符串对象 -> Managed 分配压力累积 -> GC 频繁触发
  • 增量 GC（Incremental GC）的影响：开启后 GC 拆分到多帧执行，可能观察到次数增加但单次耗时降低，需结合 GC 耗时和整体表现综合判断

定位路径

不要只看 GC 次数，应结合三点：

  1. GC 触发时间点 - UWA GOT Online 报告查看 GC 发生趋势，确认集中的时间段
  2. Managed 内存变化趋势
  3. 对应业务逻辑执行情况 - 是否发生在战斗 Tick、UI 刷新等高频逻辑

GC 峰值与某段逻辑高度重合 -> 检查该路径上的内存分配。

优化方向

减少高频路径中的临时分配：

  • 避免在 Update / Tick 中频繁创建对象
  • 固定文本缓存（避免重复拼接）
  • 减少不必要的字符串处理

关键结论：比起关注"GC 调用了多少次"，更重要的是找到哪些代码在持续制造垃圾对象。

三、案例二：特效精准降温，别急着对画质动刀

背景

部分特效开启 1/4 RT 后渲染性能提升明显，GPU 压力和发热改善。考虑按 Overdraw 评分自动开启 1/4 RT。问：是否需要降低战斗场景相机分辨率降 GPU 压力？

1/4 RT vs 降场景分辨率

手段 优化范围 影响面
1/4 RT 特效自身 GPU 填充压力 仅影响该特效，画质损失局部、可控
降场景相机分辨率 整个画面渲染成本 直接影响画面清晰度，整体性手段，需谨慎

两者优化范围不同，不能互相替代。

决策路径：先确认 GPU 瓶颈来源

降场景分辨率前，结合 UWA GOT Online 报告确认：

  • GPU Clocks 是否长期处于较高水平（判断 GPU 负载）
  • Overdraw 是否随特效数量增加明显升高（透明特效叠加填充压力）
  • 开启 1/4 RT 前后 GPU Clocks、帧率、发热是否有实际改善
  • GPU 负载变化是否与特效集中出现的战斗场景保持一致

分层优化原则

  1. 先做特效精准降温（1/4 RT 按 Overdraw 阈值自动开启）
  2. 特效优化后 GPU 仍高（场景渲染、后处理、UI 等占比较大）-> 再考虑降分辨率 / 调画质档位
  3. 目标：GPU 消耗、画面质量、设备发热三者平衡，而非单纯降低某一项指标

四、可复用的排查思路

问题 第一直觉误区 正确切入点
GC 频繁 盯 GC 次数 / 找谁调了 GC.Collect 找高频路径中持续制造临时对象的代码
GPU 压力高 直接降场景分辨率 先定位瓶颈是特效 Overdraw 还是整体渲染，分层施策

附：方案审校

案例一审校

✅ 正确。 "GC 不需要显式调用，持续临时对象分配就会触发"是 Unity 托管堆 GC 的基本机制。高频路径字符串拼接产生垃圾是经典 GC 元凶，判断准确。增量 GC 导致"次数增、单次降"的说明也正确--增量 GC 将 Stop-The-World 拆分为分帧执行，单次停顿变小但触发更频繁。

⚠️ 补充风险点： - 字符串拼接除 + 外，string.Format、StringBuilder.ToString()、Lambda 捕获（闭包产生对象）也是常见隐形分配，排查时应一并关注 - 增量 GC 的"次数增加"在 Unity Profiler 中可能表现为 GC Alloc 曲线形态变化，需注意帧间分配阈值触发逻辑，不能只看总次数 - 除字符串外，高频路径中常见分配还有：LINQ（产生中间集合）、foreach 某些容器的装箱、协程 yield return new WaitForSeconds()（每帧 new 对象） - 文章未提及对象池这一根本性解法，对于必须频繁创建的对象（如特效实例、子弹、伤害数字），对象池比"减少分配"更彻底

🔧 可行性： 高。UWA GOT + Profiler 定位 GC 分配路径是标准方法。

案例二审校

✅ 正确。 1/4 RT 降特效分辨率减少 Fragment 填充，对高 Overdraw 特效收益明显，判断准确。"降场景分辨率是整体性手段，需谨慎"的建议合理。按 Overdraw 评分自动开启 1/4 RT 是务实的分级策略。

⚠️ 补充风险点： - 1/4 RT 会降低特效清晰度，UI 特效、文字类特效不宜使用（会出现明显锯齿/糊化），自动开启策略需排除这类特效 - 1/4 RT 的降采样与上采样过程本身有开销，特效覆盖范围小或 Overdraw 低时可能反而更慢，阈值设定需实测 - 降场景分辨率除影响清晰度外，还会影响后处理、UI 渲染到 RT 的链路，可能引入新的渲染顺序问题 - 文章提到"调整画质档位"作为后备手段，但未说明档位切换的运行时开销（可能触发资源重新加载 / Shader 切换），实际需评估切换瞬间的卡顿

🔧 可行性： 高。分层优化思路（先特效精准降温，再整体降级）是正确的工程实践。

综合结论

维度 评价
技术深度 良好，准确区分 GC 触发机制与 1/4 RT / 降分辨率的优化范围
正确性 核心判断无误，无原理性错误
可落地性 高，定位路径与分层优化思路具体可操作
风险披露 良好，明确说明降分辨率影响画面清晰度需谨慎

没有发现原理性错误。 主要提醒：GC 排查要扩展到 LINQ/闭包/协程等隐形分配，并考虑对象池；1/4 RT 自动开启需排除 UI/文字特效并实测阈值。
